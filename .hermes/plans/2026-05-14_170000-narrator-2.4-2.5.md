## Goal

Que SECOPPAL responda con una narrativa natural en lugar de una lista de ítems.

En vez de:
  "Encontré 5 resultados:
   1. Mantenimiento vial corredor principal
   Entidad: Gobernación del Atlántico
   Valor: $750.000.000 | Abierto
   ..."

Responda:
  "Encontré 5 procesos abiertos de mantenimiento vial en el Atlántico.
   El de mayor valor es el del corredor principal, publicado por la Gobernación
   por $750M. También hay uno de la Alcaldía de Barranquilla por $200M.
   ¿Quieres ver los detalles de alguno?"

El LLM narra SOBRE el payload real de SECOP — nunca inventa datos.
Este es el principio de grounding: todo lo que dice el LLM debe estar
en los rows que le pasamos. Si no está en los datos, no lo dice.

Alcance de esta tarea:
  - Clase NarratorHandler (nuevo módulo)
  - Integración en orchestrator como action opcional post-format
  - Formateador narrativo por canal (2.5 se hace en el mismo paso — es trivial
    una vez que el narrador existe)
  - Feature flag: si LLM no está habilitado o falla, fallback al formato lista actual

## Contexto actual

- LLMHandler existe en app/core/llm_handler.py — cliente DeepSeek, tool-calling
- Formatter.format_for_channel devuelve (str, list[dict]) — la str es la respuesta actual
- orchestrator.format_response action: llama formatter, retorna formatted_response
- El pipeline no tiene step de narración — format_response es el final
- settings.deepseek_api_key + settings.llm_enabled controlan si el LLM está activo

## Qué NO hace el narrador (limites de scope)

- NO analiza patrones estadísticos (eso es 2.6 — observer)
- NO genera sugerencias de seguimiento (eso es 2.8)
- NO referencia turnos anteriores de la conversación
- NO inventa datos que no estén en los rows
- NO corre si hay 0 resultados (el mensaje de "sin resultados" ya es bueno)
- NO reemplaza las URLs — las incluye en la respuesta final

### Prompt del narrador

El prompt pasa los datos como JSON compacto. Instrucciones:
1. Describe qué encontraste en 2-3 oraciones (sin repetir cada ítem)
2. Menciona el más relevante (mayor valor o más reciente)
3. Si hay más resultados que los mostrados (total_count > len(rows)), mencionarlo
4. No inventes datos — solo usa lo que está en los items
5. No incluyas URLs en la narrativa — se agregan por separado
6. Máximo 4 oraciones. Tono: profesional pero directo. Tutear al usuario.
7. Responde SOLO la narrativa, sin prefijos ni saludos

Payload al LLM (grounding):
```json
{
  "tipo": "procesos | contratos",
  "total_en_secop": 347,
  "mostrando": 5,
  "filtros_aplicados": {"departamento": "ATLÁNTICO", "objeto": ["mantenimiento"]},
  "resultados": [
    {"titulo": "...", "entidad": "...", "valor": "$750.000.000", "estado": "Abierto"},
    ...
  ]
}
```

### Límites de tokens
- Input al narrador: máximo ~800 tokens (5 rows caben bien)
- Output esperado: 60-120 palabras
- Timeout: 10s (más corto que el parser — la narrativa es best-effort)
- Si timeout o error → retornar None → usar respuesta del formatter como fallback

## Formateador narrativo (2.5 integrado)

La narrativa del LLM reemplaza SOLO el bloque de texto introductorio.
Las URLs de los resultados se mantienen al final, numeradas, como referencia.

Estructura del output final:
```
[NARRATIVA DEL LLM — 2-4 oraciones]

Referencia rápida:
1. [título truncado] — [URL]
2. [título truncado] — [URL]
...
```

Por canal:
- telegram: narrativa + lista de URLs (texto plano, sin markdown bold)
- whatsapp: narrativa + lista con emojis básicos
- streamlit: solo retorna la narrativa (la tabla/tarjetas se muestran por separado en la UI)

## Integración en orchestrator

Nueva action en Burr:
```python
@action(reads=["formatted_response", "formatted_rows", "dataset_id", "channel",
                "resolved_params", "total_count"],
        writes=["formatted_response"])
def narrate_response(state, narrator):
    if not narrator.enabled or not state["formatted_rows"]:
        return state  # fallback: mantener formatted_response del formatter
    narrative = narrator.narrate(
        rows=state["formatted_rows"],
        dataset_id=state["dataset_id"],
        params=state.get("resolved_params", {}),
        channel=state["channel"],
        total_count=state.get("total_count", 0),
    )
    if narrative is None:
        return state  # fallback silencioso
    # Ensamblar: narrativa + referencias de URLs
    final = _assemble_narrative_response(narrative, state["formatted_rows"], state["channel"])
    return state.update(formatted_response=final)
```

narrate_response corre DESPUÉS de format_response:
  degrade_query → format_response → narrate_response → [halt]

halt_after actualizado: ["narrate_response", "clarify_query"]

Si narrator.enabled es False → narrate_response hace pass-through sin llamar al LLM.

## Validación de grounding — implementación

Enfocada en cifras monetarias, no en nombres de entidad.
Los montos son exactos en los datos y los más peligrosos si se inventan.
Los nombres de entidad se parafrasean legítimamente (falsos positivos si se validan).

```python
def _validate_grounding(narrative: str, rows: list[dict]) -> bool:
    """Verifica que las cifras monetarias mencionadas en la narrativa
    correspondan (con tolerancia ±1%) a valores reales de los rows.
    Retorna True si la narrativa pasa, False si hay cifra inventada."""
    real_values = _extract_real_values(rows)       # set de floats
    narrative_values = _extract_narrative_values(narrative)  # set de floats
    for val in narrative_values:
        if not any(abs(val - real) / max(real, 1) <= 0.01 for real in real_values):
            return False
    return True
```

Formatos que el LLM alterna — ambos lados se normalizan a float antes de comparar:
  $750.000.000    → 750_000_000.0
  $750M           → 750_000_000.0
  $750 millones   → 750_000_000.0
  750M COP        → 750_000_000.0
  $1.5MM          → 1_500_000_000.0
  $1.5 mil millones → 1_500_000_000.0
  $1,500M         → 1_500_000_000.0

Tolerancia ±1% absorbe redondeos legítimos ("aproximadamente 750M" cuando el real es 749.800.000).

Flujo con validación:
  narrativa = narrate(rows, ...)
  if not _validate_grounding(narrativa, rows):
      narrativa = narrate(rows, ..., strict=True)  # segundo intento, prompt más estricto
      if not _validate_grounding(narrativa, rows):
          return None  # fallback al formatter clásico

## Regla de grounding — qué puede decir el narrador

PUEDE:
  - Mencionar conteo total (de total_count)
  - Mencionar entidades, valores, estados que aparecen en los rows
  - Comparar valores entre ítems que están en los rows
  - Mencionar que hay más resultados de los mostrados

NO PUEDE:
  - Afirmar cosas sobre contratos que no están en los rows
  - Dar un porcentaje o estadística que no se derive directamente del payload
  - Recomendar un proveedor específico
  - Opinar sobre la legitimidad o calidad de un proceso

La regla se implementa en el prompt del sistema, no en código.
Si el LLM viola la regla → el usuario lo verá. No hay validación automática en v1.2.
Esto es aceptable para MVP. Validación en v1.3.

## Riesgos y decisiones

RIESGO 1: latencia — narración suma ~1-2s al pipeline
  MITIGACION: timeout de 10s, fallback silencioso al formatter.
  Si el LLM tarda → el usuario recibe la lista clásica sin error.

RIESGO 2: narrativa genérica o repetitiva
  MITIGACION: el prompt especifica máximo 4 oraciones, mencionar el más relevante,
  no repetir todos los ítems. En la práctica hay que probar y ajustar.

RIESGO 3: costo API en producción
  MITIGACION: la narrativa solo corre si narrator.enabled. Por defecto deshabilitado
  si no hay api_key. Se puede controlar con settings.llm_enabled.

DECISION: narrate_response comparte la misma api_key que LLMHandler (DeepSeek).
  No hay segunda key ni segundo modelo. Un LLM, dos usos: parseo y narración.
  Si se quiere separar en el futuro → NarratorHandler acepta model override.

DECISION: 2.5 (formateador narrativo por canal) se implementa DENTRO de narrator.py
  como helper _assemble_narrative_response(narrative, rows, channel) -> str.
  No es un módulo separado — es trivial una vez que la narrativa existe.
